# ROS 2 simulation integration

The Unity bridge uses the ROS 2 rosbridge WebSocket protocol. It is opt-in and
does not drive a physical robot. The existing Python training backend still
coordinates operations and confirms progress with Unity.

## Start a ROS host

ROS 2 and WSL are not installed on the current Windows PC. Use an existing ROS 2
Linux machine, or provision a ROS environment separately. On Ubuntu with a
supported ROS 2 distribution installed and sourced:

```bash
sudo apt install ros-$ROS_DISTRO-rosbridge-suite
ros2 launch rosbridge_server rosbridge_websocket_launch.xml
```

The default WebSocket address is `ws://127.0.0.1:9090`. Use the ROS host address
when Unity and ROS run on different machines. This prototype has no command
authentication: use localhost or a trusted isolated development network.

## Start Unity

1. Start the backend with `backend/start.ps1`.
2. Open `Assets/Scenes/GearboxTraining.unity` and enter Play Mode.
3. Select **Tools > Gearbox Demo > ROS 2 > Connect Simulation Bridge**. This
   creates a runtime component and selects it in the Inspector. Its `Bridge Url`
   defaults to localhost; change it before the component starts by setting
   `GEARBOX_ROSBRIDGE_URL` before launching Unity instead for a remote host.

For automatic connection, set this environment variable in the process launching
Unity:

```powershell
$env:GEARBOX_ROSBRIDGE_URL = 'ws://127.0.0.1:9090'
```

The simulation still waits for readiness once, then progresses automatically.
Pause and Resume work locally. Reset returns to waiting for readiness. No Stop
voice command or button is reintroduced by this bridge.

## Topics

| Topic | ROS 2 type | Direction |
| --- | --- | --- |
| `/gearbox/simulation/joint_states` | `sensor_msgs/msg/JointState` | Unity to ROS, 10 Hz |
| `/gearbox/simulation/state` | `std_msgs/msg/String` | Unity to ROS, JSON workflow state, 10 Hz |
| `/gearbox/simulation/control` | `std_msgs/msg/String` | ROS to Unity, JSON control |
| `/gearbox/simulation/control_ack` | `std_msgs/msg/String` | Unity to ROS, JSON dispatch acknowledgement |

Joint positions are actual ArticulationBody joint positions, converted from
degrees to radians. Joint names are `simulation_joint_1` through
`simulation_joint_6`. They describe the current simulation rig, not calibrated
Yaskawa joint coordinates. No physical `/joint_states`, joint trajectory action,
or controller command topic is used. Time stamps use UTC wall time; this does not
publish `/clock` or implement ROS simulated time.

Control payload example (inside the String message's `data`):

```json
{"request_id":"unique-request-1","action":"ready"}
```

Allowed actions: `ready`, `pause`, `resume`, `reset`. Each new action needs a
unique request ID. Recent IDs are deduplicated (256, within one Unity runtime).
`dispatched` means handed to Unity's training client, not successfully completed.
Observe `/gearbox/simulation/state` for actual progress. A backend error can occur
after dispatch. A dropped connection reconnects but does not replay queued
commands. Local simulation continues if ROS monitoring disconnects.

## ROS command client

Copy `ros2/gearbox_training` into a ROS workspace's `src/` folder, then:

```bash
colcon build --packages-select gearbox_training
source install/setup.bash
ros2 run gearbox_training control ready
ros2 run gearbox_training control pause
ros2 run gearbox_training control resume
ros2 run gearbox_training control reset
ros2 topic echo /gearbox/simulation/joint_states
ros2 topic echo /gearbox/simulation/state
```

The client waits up to ten seconds for a matching acknowledgement and does not
retry motion. It reports failure if no Unity subscriber/acknowledgement appears.

## Verification on this PC

Unity 6000.6.0f1 compiled the integration and imported all seven meshes. The
local WebSocket protocol peer passed Ready -> Pause -> Resume -> Reset, invalid
command rejection, duplicate ID handling, and six-joint telemetry (14 messages).
This is a transport/workflow test, not a test of a running ROS graph or controller.

To repeat, keep the backend running and close this project's Unity editor:

```powershell
python tools/rosbridge_protocol_check.py
```

In a second terminal:

```powershell
& 'C:/Program Files/Unity/Hub/Editor/6000.6.0f1/Editor/Unity.exe' -batchmode -nographics -projectPath (Get-Location).Path -executeMethod GearboxDemo.Editor.GearboxRosChecks.RunBatch -logFile .simulation-check/ros-unity.log
```

Do not add `-quit`; the runner exits itself. Report:
`.simulation-check/ros-protocol.json`. The test peer requires the Python
`websockets` package. The CAD preview prefab is regenerated by this check.

## Imported CAD

`Assets/Models/YaskawaRobot` contains the seven supplied IGES components converted
to metre-scale OBJ meshes. Source files were read only; `conversion.json` records
their SHA-256 hashes, triangle counts, and bounds. The source is Y-up; X is
reflected for Unity. The OBJ importer is configured explicitly for this mapping.

Use **Tools > Gearbox Demo > Yaskawa > Create CAD Preview Prefab** outside Play
Mode to assemble the reference geometry.

The main `Assets/Scenes/GearboxTraining.unity` now uses the CAD geometry on a
six-joint articulation, with the existing gripper and training controls. The
original scene is retained as `GearboxTraining_PrimitiveBackup.unity`.
`YaskawaSimulationBuilder.cs` records the estimated joint pivots, axes, limits,
masses, and flange offset. `YaskawaSimulationRig` identifies this approximation.
The robot uses its original CAD scale on a shared tabletop, with the parts tray
immediately beside its base and two nearby assembly stations. The earlier enlarged
display scale and floor pedestal have been removed. This is still an approximate
simulation and needs confirmed joint definitions, dynamics, and tool transform
before it can serve as a calibrated digital twin. CAD alone does not
supply a validated ROS driver. Published joint states describe this simulation,
and must not be sent to physical hardware as joint commands.

Tabletop verification: all 13 individual assembly operations and backwards
checkpoint restoration passed. The extended replay reached operation 10 before
the previous 420-second test deadline; it reported no additional motion fault.
The CAD test deadline is now 900 seconds for future full regression runs. The
extended replay has not yet been verified to completion. Recorded results:
`.simulation-check/tabletop-workflow-results.txt`.

Reproduce conversion:

```powershell
python -m pip install --target .tools/cad-python cadquery-ocp
python tools/convert_robot_cad.py '<folder containing base_view_*.igs and six axis files>'
```

## Physical robot follow-up

The robot and controller model, supported driver, network configuration, and
manufacturer joint definitions are still required. The next step is a reviewed
URDF and real controller diagnostics connection, followed by controlled motion
integration. This bridge intentionally has no route from simulation topics to a
physical arm.
